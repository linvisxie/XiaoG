# XiaoG Project Governance Manual v3.0

版本：v3.0\
定位：XiaoG项目长期开发与治理规范\
适用范围：所有后续开发、架构调整、版本迭代、Codex协作。

------------------------------------------------------------------------

# 一、文档目的

本文件规定 XiaoG 后续如何进行：

-   需求管理
-   开发协作
-   架构决策
-   开源复用
-   版本发布
-   风险控制

目标：

保证 XiaoG 在长期发展过程中保持：

-   架构稳定
-   决策连续
-   开发可追踪
-   核心控制权不丢失

------------------------------------------------------------------------

# 二、项目治理原则

## 1. Core First

任何功能开发首先判断：

是否增强 XiaoG 核心能力。

优先：

-   Runtime能力
-   Provider能力
-   数据体系
-   Agent能力

避免：

为了短期展示开发外围功能。

------------------------------------------------------------------------

## 2. Product Before Expansion

顺序：

    核心能力

    ↓

    个人稳定使用

    ↓

    内部测试

    ↓

    外部部署

    ↓

    规模扩展

禁止：

为了部署、展示、技术验证提前扩大复杂度。

------------------------------------------------------------------------

## 3. Local First

默认：

用户数据属于用户。

设计优先：

-   本地存储
-   用户控制
-   数据可迁移

云端能力需要额外设计。

------------------------------------------------------------------------

## 4. Capability Driven

UI不绑定具体模型。

流程：

    Provider

    ↓

    Capability Metadata

    ↓

    动态UI

禁止：

提前为某个模型创建专属功能入口。

------------------------------------------------------------------------

# 三、Single Codex Development Workflow

正式采用：

## Single Codex Governance

一个Codex负责：

-   代码修改
-   测试执行
-   提交记录
-   状态报告

ChatGPT负责：

-   架构设计
-   任务规划
-   技术评估
-   代码审查

------------------------------------------------------------------------

# 四、Codex任务执行规范

每个开发任务必须包含：

## 1. 背景

说明：

-   当前问题
-   所属阶段
-   目标

------------------------------------------------------------------------

## 2. 修改范围

明确：

允许修改：

-   哪些文件
-   哪些模块

禁止：

-   未授权扩大范围

------------------------------------------------------------------------

## 3. 验证要求

必须报告：

-   测试结果
-   修改文件
-   Commit
-   工作树状态

------------------------------------------------------------------------

## 4. 风险说明

必须说明：

-   潜在影响
-   未验证部分
-   后续建议

------------------------------------------------------------------------

# 五、需求进入规则

任何新需求进入开发前，需要判断：

## A. 是否属于核心能力？

如果是：

进入Roadmap。

------------------------------------------------------------------------

## B. 是否可以通过开源复用？

如果不是核心：

优先寻找成熟方案。

------------------------------------------------------------------------

## C. 是否会增加长期维护成本？

评估：

-   代码复杂度
-   依赖风险
-   License风险
-   固定成本

------------------------------------------------------------------------

# 六、开源组件引入规范

采用：

## Open Source Reuse Framework

流程：

    需求出现

    ↓

    价值判断

    ↓

    开源搜索

    ↓

    License检查

    ↓

    POC

    ↓

    Adapter设计

    ↓

    是否集成

------------------------------------------------------------------------

优先：

-   MIT
-   Apache-2.0
-   BSD

------------------------------------------------------------------------

禁止：

-   为了先进性堆组件
-   让第三方控制核心架构
-   引入固定月成本

------------------------------------------------------------------------

# 七、架构变更规则

重大架构修改必须回答：

1.  为什么现有架构无法满足？
2.  是否有更简单方案？
3.  是否影响已有能力？
4.  是否可以通过Adapter解决？

------------------------------------------------------------------------

优先：

    Adapter

    >

    模块扩展

    >

    核心重构

------------------------------------------------------------------------

# 八、版本管理规范

版本体系：

## 0.x阶段

快速建设与完善。

------------------------------------------------------------------------

当前：

## 0.4.4

Local Runtime Baseline。

------------------------------------------------------------------------

未来：

## 0.5.0

Provider Ecosystem。

## 0.6.0

Personal Runtime Complete。

## 0.7.0

Internal Beta。

------------------------------------------------------------------------

每个版本必须记录：

-   目标
-   完成功能
-   验收标准
-   已知风险

------------------------------------------------------------------------

# 九、Git管理规范

采用：

## Minimal Git Governance

保留：

-   main分支
-   commit历史
-   version tag
-   changelog

暂不：

-   复杂分支模型
-   复杂CI/CD

------------------------------------------------------------------------

提交要求：

Commit应描述：

-   功能变化
-   修复内容
-   架构调整

------------------------------------------------------------------------

# 十、测试与发布规范

每次重要修改后：

检查：

-   核心测试
-   编译检查
-   前端检查
-   回归测试

报告：

必须包含：

-   PASS/FAIL
-   未覆盖部分

------------------------------------------------------------------------

# 十一、日志与状态记录规范

长期维护必须保留：

## Baseline Report

记录：

-   当前版本
-   Commit
-   Runtime状态
-   已完成事项

------------------------------------------------------------------------

## Decision Log

记录：

-   为什么改变方向
-   为什么否决方案

------------------------------------------------------------------------

## Roadmap

记录：

-   未来计划

------------------------------------------------------------------------

三者共同组成项目记忆。

------------------------------------------------------------------------

# 十二、接力包规范

跨对话或跨环境时：

必须记录：

-   当前目标
-   当前状态
-   已完成
-   正在进行
-   计划
-   候选
-   已否决
-   风险
-   下一步

禁止：

-   保存密码
-   保存API Key
-   保存Token

------------------------------------------------------------------------

# 十三、重大方向判断标准

未来所有技术选择遵循：

## 是否增强用户价值？

## 是否保持XiaoG核心控制权？

## 是否降低长期复杂度？

## 是否支持未来扩展？

如果不能明确提升长期价值，则暂缓。

------------------------------------------------------------------------

# 十四、最终治理目标

XiaoG长期目标：

成为一个：

-   可持续开发
-   可扩展
-   用户控制
-   长期维护

的个人 AI Runtime 系统。

治理原则：

不是最快开发。

而是：

在保持方向正确的情况下持续演进。
